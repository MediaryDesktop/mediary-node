# modules

Продуктова частина системи. Модуль — це **ownership домену**, а не тека для
файлів схожого типу.

Порожньо у фазі 0. Карта фази 1 — у
[docs/plans/desktop-implementation-plan.md](../../../../docs/plans/desktop-implementation-plan.md).

## Публічний API

```
modules/library/
  index.ts        публічний контракт — короткий і свідомий
  ...             решта: як зручно
```

Зовні:

```ts
// OK
import { LibraryScreen, rescan } from '@modules/library'
// валить ESLint
import { FileRow } from '@modules/library/ui/file-row'
```

Якщо `index.ts` експортує 40 внутрішніх деталей — межі немає, є barrel.

## Внутрішня структура не нав'язується

Не треба заводити `components/ hooks/ services/ repositories/ use-cases/`
лише тому, що «так правильно». Якщо функція може жити в `model.ts` — хай живе
там. Структура з'являється, коли файл справді розпадається на дві теми, а не
за розкладом.

## Залежності

- Модуль імпортує `@core/*`, `@ui/*`, `@lib/*` і **кореневий** `@modules/<сусід>`.
- Модуль **не** імпортує `@app`.
- Модулі утворюють DAG. Цикл валить `npm run arch:check`.

Якщо два модулі «мусять» знати один одного — визнач ownership і зроби
залежність односторонньою. Взаємодія в зворотний бік передається ззовні:

```tsx
// media не знає про playback
<MediaCard onPlay={handlePlay} />
```

Третій модуль `shared-media-playback` для розв'язання циклу **не створюється**.

## Коли створювати модуль

Коли з'явилася справжня межа: окремий домен, окремий сценарій, окремий
lifecycle, окремий власник.

**Не** тому, що файл виріс до 300 рядків, компонент став великим, код
використали двічі або хочеться чистішого дерева тек. Невеликий дубль кращий за
фальшиву абстракцію — виносимо, коли з'явилася **іменована концепція з власником**.

Розмір модуля сам по собі не проблема. `playback` може бути великим і складним,
якщо вся ця складність належить playback. Проблема — коли ownership нечіткий.
