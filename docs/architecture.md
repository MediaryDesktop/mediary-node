# Архітектура renderer'а

Десктоп-клієнт — **модульний моноліт**: один застосунок і один deployment, але
функціональність розділена на модулі з чітким ownership, внутрішньою
реалізацією та публічним API.

Головний принцип:

> Межа модуля важливіша за красу структури тек.

Код групується за тим, що **змінюється разом і має спільного власника**, а не за
технічним типом файлу. Ми не будуємо шари заради шарів і не розкладаємо одну дію
на `page → feature → entity → shared`, якщо це не створює реальної межі.

---

## 1. Структура

```
src/
├── app/        композиція: роути, провайдери, каркас, багатомодульні екрани
├── modules/    домен / user-facing функціональність
├── core/       інфраструктура застосунку
├── ui/         generic візуальні примітиви
└── lib/        generic технічні примітиви
```

Це **не** п'ятирівнева ієрархія шарів. Це категоризація ownership:

```
app      = composition
modules  = domain ownership
core     = application infrastructure
ui       = generic visual primitives
lib      = generic technical primitives
```

Напрямок залежностей між категоріями при цьому односторонній — і саме ця
частина перевіряється машиною (§6).

---

## 2. Що визначає цю архітектуру: два бекенди

Найважливіший структурний факт десктопа, з якого випливає половина рішень нижче:
**renderer говорить із двома різними бекендами, і вони падають незалежно.**

|  | Хмара | Нода |
|---|---|---|
| Де | віддалена, мультитенантна | локальна, цей самий комп'ютер |
| Автентифікація | сесія користувача | процесний токен від Electron main |
| Обмеження | rate limit, CORS | немає |
| Свіжість даних | `staleTime`, refetch при фокусі | завжди свіжі |
| Інвалідація | час + мутація | **подія з WebSocket ноди** |
| Коли недоступна | каталог із кешу | локальне не працює взагалі |

Каталог мусить рендеритися, коли нода мертва. Плеєр мусить працювати, коли
хмари немає. Це вже не напрямок залежності, а **ізоляція відмов** — і тому два
з'єднання живуть окремо (`core/node`, `core/cloud`), а не за спільним фасадом,
який довелося б розгалужувати на кожному виклику.

---

## 3. app

`app/` відповідає за **композицію**: роути, провайдери, каркас застосунку,
крос-модульне wiring.

```
app/
├── main.tsx        точка входу renderer'а
├── app.tsx         provider tree + міст до Electron main
├── router.tsx      маршрути
├── providers/      контекст, оверлейний стек, wiring
├── layout/         каркас: AppLayout, індикатор стану ноди
└── screens/        екрани, що композують кілька модулів
```

`app` не володіє бізнес-логікою. Але «тонкий» він не тому, що логіки в системі
мало, а тому що **ownership логіки лежить у модулях**.

Один екран ≠ один модуль. Сторінка тайтулу — це композиція `media` (метадані з
хмари) + `library` (наявні локальні файли) + `playback` (кнопка «дивитись»).
Модуль `title-page` для цього **не створюється**: він не мав би власного домену.

Екран, що належить одному модулю, живе в тому модулі й імпортується маршрутом
напряму. Екран, що композує кілька, живе в `app/screens/`.

**Маршрут — межа code-splitting.** Barrel, який ре-експортує всі екрани, змушує
кожен роут тягнути їх усі: екрани мають Effector-моделі, тобто сайд-ефекти, і
bundler їх не відтрусить. Заміряно на попередньому клієнті: +90 kB First Load JS
**на кожному** маршруті. Тому спільного barrel для екранів немає, а самі екрани
lazy-завантажуються по мірі появи.

## 4. modules

Основна бізнес-частина. Модуль представляє cohesive домен або користувацький
сценарій і володіє всією потрібною для нього логікою.

### Публічний API

```ts
// OK
import { LibraryScreen, rescan } from '@modules/library'

// валить ESLint
import { FileRow } from '@modules/library/ui/file-row'
```

`index.ts` має бути **коротким і свідомим**. Якщо він експортує 40 внутрішніх
деталей — межі немає, є barrel. Внутрішню реалізацію можна змінювати, не
чіпаючи споживачів, рівно доти, доки це правило тримається.

### Внутрішня структура не нав'язується

Локальна структура дозволена, але не створюється автоматично. Не треба заводити
`components/ hooks/ services/ repositories/ facades/ use-cases/` лише тому, що
«так правильно». Якщо функція може жити в `model.ts` — вона живе там.

### Карта модулів фази 1

| Модуль | Володіє | Бекенд | Імпортує |
|---|---|---|---|
| `media` | каталог: пошук, фільтри, картки, метадані | хмара | — |
| `account` | ідентичність: вхід, сесія, профіль, паровані пристрої | хмара | — |
| `library` | локальні файли, зіставлення з каталогом, ручне виправлення | нода | `media` |
| `downloads` | провайдери торентів, черга завантажень | нода | `media` |
| `playback` | mpv, стріми, позиція відтворення | нода | `media`, `library` |
| `reader` | посторінкове читання, epub | нода | `media`, `library` |
| `extensions` | плагіни (фаза 2) | нода | — |

Фільтри каталогу належать `media` — окремий модуль `filters` був би виділенням
«фічі» заради виділення. Вхід і профіль — один модуль `account`, бо це одна
концепція: розділяти `auth` і `user` заради красивого DAG означає створити межу
там, де немає окремого власника.

## 5. core

`core/` — **інфраструктура застосунку**, а не місце для «важливих» речей.

```
core/
├── node/     з'єднання з локальною нодою: міст до Electron main, URL+токен,
│             стан супервізора, HTTP-клієнт, потік подій
└── cloud/    з'єднання з хмарою: сесія, HTTP-клієнт
```

> **Core ≠ важливий модуль.**

Критичний для продукту `playback` усе одно лишається доменним модулем. Це
правило — єдине, що не дає `core/` за рік перетворитися на новий `shared/`.

Практичний розріз на прикладі ноди: **з'єднання** з нодою — інфраструктура (у
нього немає домену, воно потрібне всім). А коріння бібліотеки, тека завантажень
і налаштування плеєра — це доменні дані з реальними власниками, і вони належать
`library`, `downloads` і `playback` відповідно. Класти їх у `core` тому, що
«вони про ноду» — саме та помилка, від якої застерігає правило вище.

### Чого в `core/` поки немає — і чому

Дві теки, які напрошуються, свідомо **не створені**:

- **`core/realtime`** — зараз потік подій ноди це дванадцять рядків
  `openNodeEventStream` усередині `core/node/client.ts`. Окрема тека з'явиться,
  коли додасться перепідключення, мапінг подій в Effector і підписка по темах —
  тобто коли виникне іменована концепція з власним lifecycle.
- **`core/availability`** — похідний стан «які бекенди зараз придатні»
  (мережа + сесія + версійний гейт `client.min_supported` із хмари). Це
  призначене місце для таблиці станів із
  [desktop-implementation-plan §1.4](../../docs/plans/desktop-implementation-plan.md).
  Поки що комбінувати нема чого: є лише `$nodeReady`, і він живе в `core/node`.

Тека, що ре-експортує один стор, — це та сама фальшива абстракція, від якої
застерігає §9. З'явиться другий доданок — з'явиться тека.

## 6. ui і lib

**`ui/`** — дизайн-система: `Button`, `Input`, `Modal`, `Tabs`, `theme`, токени.
Не знає ні домену, ні інфраструктури. `MediaCard`, `DownloadButton`,
`NodeStatusBadge` тут заборонені — вони належать модулю-власнику або каркасу.

Прикордонний випадок вирішується так: `Image` з lazy-загрузкою і плейсхолдером —
це `ui`; `Image`, що вміє будувати URL постера з `media_id`, — це `modules/media`.

**`lib/`** — generic технічні утиліти: debounce, парсери, формат дат. Не знає, що
таке медіа, тайтл, торент, нода чи хмара.

Глобальний `shared/` не існує **навмисно**: це тека, назва якої не ставить
питання про власника.

## 7. Правила залежностей

| Категорія | Може імпортувати | Не може |
|---|---|---|
| `lib` | нічого | усе решта |
| `ui` | `@lib` | `core`, `modules`, `app` |
| `core` | `@lib` | `modules`, `app` |
| `modules` | `@core`, `@ui`, `@lib`, **кореневий** `@modules/<сусід>` | `app` |
| `app` | усе | — |

### Модулі не утворюють циклів

Якщо два модулі потребують один одного — **не** створюємо третій
`shared-media-playback`. Спочатку визначаємо ownership і робимо залежність
односторонньою.

Канонічний приклад:

```
playback → media          ✅
media ──X──► playback     ❌
```

`playback` користується `media` для ідентичності тайтла, метаданих і компонентів.
`media` про `playback` не знає. Якщо картці потрібна кнопка «дивитись» —
взаємодія передається ззовні:

```tsx
<MediaCard onPlay={handlePlay} />
```

Так `media` знає, **як показати** медіа, але не знає, **як працює** відтворення.

Причина тут сильніша за естетику графа: `media` живе з хмари, `playback` — з
ноди. Ребро в зворотний бік зробило б каталог непрацездатним при мертвій ноді.

## 8. Enforcement

Межі мають бути **executable rule**, а не побажанням у документації. Два
інструменти, бо вони ловлять різні речі:

| Інструмент | Що бачить | Що ловить |
|---|---|---|
| ESLint `no-restricted-imports` | один файл | **напрямок** імпортів, глибокі крос-модульні шляхи |
| `scripts/check-architecture.mjs` | увесь граф (Tarjan SCC) | **цикли** |

Цикл `library ↔ media` не порушує жодного правила в окремо взятому файлі:
`library/lib/*` імпортує `media/types`, `media/ui/*` імпортує `library` — обидва
легальні поодинці й утворюють цикл разом. ESLint цього структурно не бачить, і
`eslint-plugin-boundaries` теж: цикл — властивість графа. Тому потрібні обидва.

`npm run arch:check` запускає їх разом. Порушення — `error`, не `warning`.

**Детектор циклів ігнорує `import type`.** Спільні доменні типи живуть у модулі,
який ними володіє (`MediaId` — у `media`), тож крос-модульні типові імпорти
нормальні й часті. `verbatimModuleSyntax` стирає `import type { A } from 'x'`
повністю — ребра в рантаймі немає, і рахувати його означало б повідомляти про
цикли, яких не існує. Форма `import { type A }` при цьому лишається справжнім
ребром і рахується.

**Аліаси мають збігатися у п'яти місцях:** `electron.vite.config.ts`,
`tsconfig.web.json`, `vitest.config.ts`, `eslint.config.mjs` і
`check-architecture.mjs`. Розсинхрон між ними — тихий баг, тож при додаванні
категорії треба пройти всі п'ять.

## 9. Дві межі, специфічні для десктопа

### Renderer ніколи не імпортує `electron/`

Це різні процеси. Імпорт, який «наче працює», затягнув би код renderer'а в
main-процес. Форситься правилом у [eslint.config.mjs](../desktop/eslint.config.mjs).
`window.mediary` типізується через
[core/node/bridge-types.ts](../desktop/src/core/node/bridge-types.ts) —
структурну копію контракту preload'а, а не імпорт із нього.

### Generated API types не визначають архітектуру

`schema.gen.ts` в обох `core/*` — це форма чужої специфікації. Вона живе поруч із
клієнтом, який її споживає, і **не** диктує форму бізнес-коду: модуль оголошує
власні типи там, де вони мають сенс для домену, і мапить згенеровані на них.

## 10. Коли створювати модуль

Коли з'явилася **реальна межа**: окремий домен, окремий сценарій, окремий
lifecycle, окремий власник, незалежна зона змін.

**Не** тому, що:

- файл виріс до 300 рядків;
- компонент став великим;
- хочеться «чистішої» структури;
- код використали двічі;
- два файли мають однакові типи.

> Дублювання краще за фальшиву абстракцію.

Виносимо код, коли з'явилася **іменована концепція з власником**, а не тому, що
два шматки схожі.

### Товщина не є проблемою

`modules/playback` може бути великим і складним — це нормально, якщо вся ця
складність належить playback. Так само екран на 300 рядків може бути цілком
здоровим.

Проблема виникає не тоді, коли файл великий. Проблема виникає, коли **ownership
нечіткий**.

## 11. Перевірка

```bash
npm run arch:check     # цикли між модулями + напрямки залежностей
npm run typecheck      # обидва TS-проєкти: node і web
npm run test
npm run build          # ловить регресії збірки
```

## 12. Інваріанти перед merge

- Чи має код зрозумілого власника?
- Чи не потрапила доменна логіка в `ui/`?
- Чи не потрапило продуктове знання в `lib/`?
- Чи не потрапили доменні дані в `core/` тому, що «вони важливі»?
- Чи не імпортує код внутрішні файли чужого модуля?
- Чи не з'явився цикл?
- Чи лишається публічний API модуля маленьким?
- Чи стан лежить біля домену, який ним володіє?
- Чи не створюється `shared/` для уникнення питання про власника?
- Чи ловить порушення тулінг, а не тільки рев'ю?
